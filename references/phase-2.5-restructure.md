# Phase 2.5 · 结构重排（Outline Restructure）

> **v4.24 新增。** 位置：Phase 2（多文档合并）之后、Phase 3（HTML 渲染）之前。
> 作用：把「一堆平铺的 H3 知识点」重建成「H3 主题分组 + H4 知识点」两级骨架，
> 让长文档真正可读。
>
> 相关脚本：`scripts/restructure_outline.py`
> 相关门禁：`H3_PER_H2_MAX` / `H3_TOTAL_MAX` / `H4_PER_H3_MAX` / `H4_TOTAL_MAX` /
> `NO_SESSION_LABEL_IN_HEADING` / `NO_SINGLE_SUBHEADING`

---

## 0. 什么情况下必须跑

满足任意两条就跑：

- H3 总数 > 60，或 > 文档字符数 / 3000；
- 单个 H2（章）下 H3 数 > 18；
- **H4 总数为 0 或极少**，同时 H3 数很大 —— 典型的「两层骨架塌陷成一层」；
- 同章 H3 之间明显可以归成 3–10 个主题（凭目录扫一眼就能看出来）；
- 标题里出现「第一天上午 / 第二天下午2」这类 ASR 场次标签。

先跑诊断，不要凭感觉：

```bash
python scripts/restructure_outline.py <cleaned.md> --audit --report struct_audit.md
```

`--audit` 会打印并写出：H1/H2/H3/H4 计数、逐章 H3 分布、疑似可合并的同主题簇、
被写进标题的场次标签，以及每条门禁预算的当前值与超出量。

## 1. 为什么会长成 434 个 H3（2026-10-28 复盘，必读）

一次真实的「阿呆万相台无界 2 天课程」笔记（194,315 字符）交付后，结构是
**H1=1 / H2=6 / H3=434 / H4=0**，第 1 章 138 个 H3、第 2 章 163 个。
读者在目录里看到的是 434 条并列标题，等于没有结构。

复盘出四个原因，**只有第一个是硬性的，其余三个放大了它**：

### 1.1 门禁事实上禁用了 H4 层（根因）

`verify_all.py` 旧阈值：

```python
H4_PER_H3_MAX = 3     # 单个 H3 下最多 3 个 H4
H4_TOTAL_MAX  = 50    # 全文最多 50 个 H4
```

一个 19 万字符、400+ 知识点的文档，全文只允许 50 个 H4 ⇒ **平均每章 8 个 H4**。
于是「每个知识点一个标题」这个朴素诉求，只能全部落在 H3 上。
`H4_PER_H3_MAX=3` 进一步限制：即使你想用 H4，一个 H3 也只能挂 3 个，
挂第 4 个就 FAIL。

叠加两条既有规则：

- `NO_SINGLE_SUBHEADING`：H3 下只挂 1 个 H4 且无引言段 → FAIL；
- 「每个 H3 至少 2 段正文」（content-rules）。

三条一叠加，唯一能通过的形状就是：**大量 H3，零个 H4**。门禁没有报错，
它只是把文档逼成了一个可读性很差的形状。

### 1.2 Phase 2 只做机械拼接，没有「重新规划骨架」这一步

`references/phase-2-merge.md` 的合并动作是：去掉各分卷的统计段 → 标题降级 → 加总 H1。
它是**保结构**的合并（N 份 H3 进来，N 份 H3 出去），
没有任何一步回答「这 N 份东西应该组织成几层、几个主题」。

分卷处理时，每一卷单独看都还算合理；合并后总量翻几倍，
结构问题才显形 —— 而这时已经没有「重排」这个阶段了。

### 1.3 技能自带的规约与实际产出差一个数量级

- `references/phase-1.7-semantic-pass.md` 写的是 H3 编号 `### 1.1`、H4 `#### 1.1.1`、
  H3 标题 ≤20 字 —— 隐含的模型是「少量 H3 分组 + 大量 H4 知识点」；
- `references/phase-1.8-frame-crop.md` 写「典型 35 个左右」H3。

规约假设 35 个，实产出 434 个，**差 12 倍**。原因是规约里的「35 个左右」
从未被写成可校验的门禁，只是叙述文字 ⇒ 无人执行、无人发现。

### 1.4 ASR 场次标签被写进标题

分卷处理天然带「第 N 天上午/下午」的溯源需求，实现时把场次直接拼到了标题里：
`### 1.116 第二天上午：高价爆款的流量筛选逻辑`。431/434 条标题带这个前缀。
场次是**溯源信息**，属于 `_handoff.md` / `_purge_stats.md`，不属于读者可见的标题。

### 1.5 教训（写进检查清单）

> **门禁阈值是按「小文档」拍的固定值，文档规模涨一个数量级，
> 它就从「防碎片化」翻转成「强制扁平化」。**
> 任何「每 X 最多 N 个」的阈值都必须随文档规模比例化，
> 并且要为**每一层标题**都设预算 —— 只压制某一层，压力会全部挤到相邻层。

## 2. 目标结构

```
# 文档标题                        H1 × 1
## 1 章                            H2 × 3–6（按内容分章，不是按场次）
### 1.1 主题分组                   H3 × ≈8/章，全章合计 ≤ 18
#### 1.1.1 知识点                   H4 × 3–18/组，承载原来的 H3
正文…
```

预算（`restructure_outline.py` 与 `verify_all.py` 共用同一组常量）：

| 层 | 规则 | 预算 | 说明 |
|---|---|---|---|
| H2 | `H2_PER_DOC_MAX` | 15 | 章节数，按内容分章 |
| H3 | `H3_PER_H2_MAX` | 18 | 单章分组数 |
| H3 | `H3_TOTAL_MAX` | `max(20, 字符数/3000)` | 全文分组数 |
| H4 | `H4_PER_H3_MAX` | 18 | 单组知识点数 |
| H4 | `H4_TOTAL_MAX` | `max(50, 字符数/400)` | 全文知识点数 |

判据换算（19 万字符文档）：H3 预算 ≈ 64，H4 预算 ≈ 485。
即「≈60 个主题分组 + ≈450 个知识点」是健康形状，
而 434 个 H3 / 0 个 H4 同时踩爆 `H3_TOTAL_MAX`。

## 3. 四步流程

### Step 1 · 诊断

```bash
python scripts/restructure_outline.py <cleaned.md> --audit --report struct_audit.md
```

看 `struct_audit.md` 的三块：逐章 H3 分布 / 场次标签命中数 / 超出预算的规则。
若 `--audit` 显示已经合规，跳过本阶段。

### Step 2 · 导出逐章待分组清单

```bash
python scripts/restructure_outline.py <cleaned.md> --plan-out plan_dir/
```

每章生成一个 `plan_dir/chN.json`，内容只有 `idx | 干净标题`（**不带正文预览**）：
带正文会让单章 prompt 超 8000 字符上限（163 条 × 标题 ≈ 3.3K 字符，加预览就爆）。

### Step 3 · LLM 语义分组（**必须 LLM，禁止 regex**）

调用方负责调 LLM，脚本只负责校验与落地。要求 LLM 输出：

```json
{"groups":[{"title":"组名","intro":"1-2 句导语","items":[12,13,14]}]}
```

Prompt 硬约束（照抄，实测有效）：

- 同组条目必须**逻辑同主题**（同一条决策链 / 同一套方法 / 同一个场景 / 同一结论簇），
  不得因「都提到流量」「都提到人群」这类字面相似就凑组；
- 组名 8–18 字，概括「解决什么问题」，不照抄任何条目名，不带编号，不带场次词；
- `intro` 1–2 句，说明本组在章内的位置与作用，不复述组名，不写「本节介绍……」；
- 所有 idx **恰好出现一次**，不得重复/遗漏/新增；
- 组间与组内顺序按原文 idx 递增；
- 单组 3–10 条（硬上下限：`GROUP_MIN_ITEMS=2`、`H4_PER_H3_MAX=18`）。

**单章调用**：一章一个 prompt（跨章分组会破坏 H2 边界）。
**失败回灌**：校验失败时把问题清单拼回 prompt 重试，上限 3 次（实测第 2 次即收敛）。
**必须缓存**：每章结果落 `plan_dir/groups_chN.json`，LLM 贵且不稳定，重跑只补失败章。

### Step 4 · 校验并应用

```bash
# 先只校验，不写盘
python scripts/restructure_outline.py <cleaned.md> \
  --apply-plan plan_dir/plan.json --out restructured.md --check-only

# 校验通过后真正写盘
python scripts/restructure_outline.py <cleaned.md> \
  --apply-plan plan_dir/plan.json --out restructured.md
```

`validate_plan()` 的守恒校验（任何一条不过就拒绝应用）：

1. 每章都有 groups，且组数 ≤ `H3_PER_H2_MAX`；
2. 每组 `items` 非空、条数在 `[GROUP_MIN_ITEMS, H4_PER_H3_MAX]`；
3. idx **并集 == 该章全集**（无遗漏）；
4. 无重复 idx；
5. idx 顺序严格递增（禁止把后面的条目提到前面）；
6. 组名非空、不含场次标签；
7. 章节归属正确（某章的 idx 不能出现在别章的组里）。

`apply_plan()` 重建标题：H3 用 `N.M`，H4 用 `N.M.Z`，组内首个 H4 之前插入组 `intro`。
写盘走**原子写**（`.tmp` + `replace`），失败不留半成品。

## 4. 与门禁的配合

重排后必须重跑：

```bash
python scripts/verify_all.py <cleaned.md>
python scripts/regression_test.py
```

| 门禁 | 重排后的期望 |
|---|---|
| `H3_TOTAL_MAX` | PASS（分组数进预算） |
| `H3_PER_H2_MAX` | PASS（每章 ≤18） |
| `H4_TOTAL_MAX` | PASS（原 H3 数量 ≤ 比例化预算） |
| `H4_PER_H3_MAX` | PASS（单组 ≤18） |
| `NO_SINGLE_SUBHEADING` | PASS（组内 ≥2 条，或组有 intro） |
| `NO_SESSION_LABEL_IN_HEADING` | PASS（场次标签已剥离） |
| `NO_NESTED_NUMBERING` | PASS（不产生 H5；`N.M.Z` 是 H4） |

**序号是可推导的，不要单独维护**：`N` 来自 H2 顺序、`M` 来自组顺序、
`Z` 来自组内条目顺序，全部由脚本按当下顺序重算 ⇒ 插入/删除一组不会留下跳号。

## 5. 反模式（实测踩过）

- **不要用 regex / 标题相似度机械分组**。标题是 LLM 压缩产物，两句话长得像不等于同主题，
  长得完全不像也可能是同一决策链的上下游。分组只能由 LLM 读标题列表判断。
- **不要让 LLM 直接输出改写后的全文**。它会在输出里静默丢段落、改数字、合并案例。
  只让它输出 `{组名, idx 列表}` 这种**结构化索引**，正文由脚本按 idx 搬运。
- **不要因为「组数越少越整齐」就压成 3 组**。一组 40 个知识点 = 又把 H3 变成了垃圾桶，
  只是换了个位置。单组 3–10 条是读起来舒服的区间。
- **不要保留「第 N 天上午」在任何标题里**。要溯源就写进 `_handoff.md` / `_purge_stats.md`；
  写进标题会被 `NO_SESSION_LABEL_IN_HEADING` 拦下，也会让读者以为文档按上课时间组织。
- **不要重排完不重生 HTML**。TOC、锚点、编号全部来自 md 标题，md 变了 HTML 必须重渲染，
  否则交付的 HTML 与 md 结构不一致。
- **不要用 `--check-only` 通过就直接交付**。校验只保证「结构守恒」，不保证组名质量；
  组名质量要看 `plan.json`，通读一遍 H3 列表再决定。

## 6. 已知陷阱

| 陷阱 | 现象 | 处理 |
|---|---|---|
| LLM 遗漏 idx | 校验报「遗漏 N 条」 | 回灌问题清单重试，不要手工补（会掩盖 prompt 缺陷） |
| LLM 重复 idx | 校验报「重复 idx」 | 同上；重试 3 次仍失败 ⇒ 该章条目数太多，分半处理 |
| 单章 prompt 超 8000 字符 | 后端截断 / 返回不完整 JSON | 清单只放 `idx | 标题`，不带正文预览 |
| 组名过长或带编号 | `validate_plan` 拒绝 | `clean_title()` 会剥旧编号与场次标签，但语义仍需 prompt 约束 |
| 组内 1 条 | `NO_SINGLE_SUBHEADING` 与校验双拦 | `GROUP_MIN_ITEMS=2`，1 条的组应并入相邻组 |
| 段首 `intro` 缺失 | 不影响门禁，但读起来突兀 | prompt 里明确要求 1–2 句；无把握允许空串，不要编 |
| CRLF 文件被写坏 | 全文件行尾翻转 | `read_doc()` / `atomic_write()` 全程按 bytes 处理，保留原行尾 |
